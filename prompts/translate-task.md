# 直译（translate）

基于子句分析产出中文直译，并给出实词的译法对照，通过 `submit_translation` 提交。

## 流程

1. 调 `build_translation_briefing(range)` 一次。还没有子句分析的节会报错，先做 analyze。范围较大时按自然段分批。
2. 读 `clauseView`（缩进结构）、`clauses`、`tokens`、`terms`（每个实词义项的术语表条目与既有译法）、`precedingTranslations`（前文）。
3. 逐子句翻译，组成 `translations` 数组提交。
4. 若返回 `errors` 或 `consistency`，按提示修正后**整节**重提；已写入的节不要重提。
5. 本段新确定的专名、术语，用 `upsert_glossary` 写入术语表。

## 每个子句一项

```json
{
  "clauseId": "1001001a",
  "span": 1,
  "text": "起初神创造了诸天与大地",
  "renderings": [
    {"tokens": "o010010010012", "zh": "起初"},
    {"tokens": "o010010010021", "zh": "创造"},
    {"tokens": "o010010010031", "zh": "神"},
    {"tokens": "o010010010052", "zh": "诸天"},
    {"tokens": "o010010010072", "zh": "大地"}
  ],
  "paraTitle": "神创造天地"
}
```

- `text`：直译文本。原文隐含、中文必须补出的词用 `[ ]`；NA28/UBS 双括号内的经文，译文首尾加 `〚 〛`。
- `renderings`：`clauses[].contentTokens` 中的**每个实词**都要有一条；`zh` 必须是 `text` 里实际出现的字串。
  - 几个词整体译为一个中文词时，`tokens` 写区间 `首-末`。
  - 实词有意不译时 `zh` 写 `∅` 并加 `note`。
  - 虚词可以不给 rendering。
- `alternatives`：争议处的其他译法，每条 `{text, kind, basis}`（见下文“争议”）。
- `note`：主译的取舍理由；有 alternatives 时必填。
- `paraTitle`：可选，本子句开始新段落时给出段落标题（纯文本）。
- 用了扩展工具时加 `"sources": ["ai", "ext:commentary"]`。

## 争议

`clauses[].disputes` 是系统已知的争议：

- `analysis`：子句分析标为 ambiguous 的其他读法 → **必须**给 alternatives，并在 note 写主译理由。
- `textual`：影响翻译的经文异文 → 给 `kind: "textual"` 的 alternative（异文读法的译文），或在 note 说明为何不影响译文。

此外**主动**标出其他争议（断句、句法、词义），类型与写法见 principles.md 的“争议处理”。例：

```json
{
  "clauseId": "43001005b",
  "span": 1,
  "text": "黑暗却没有胜过光",
  "note": "κατέλαβεν 取“胜过、抓住”义，与上下文光暗对立相合",
  "alternatives": [
    {"text": "黑暗却不理解光", "kind": "lexical", "basis": "καταλαμβάνω 也有“领会、明白”义（徒 4:13 的 καταλαβόμενοι）；拉丁通俗译本 comprehenderunt 采此解"}
  ],
  "renderings": [ ... ]
}
```

alternatives 的译文同样用直译标准；不需要为 alternatives 提供 renderings。

## 用词统一

`terms` 列出范围内每个实词义项（`senseKey`）：

- `glossary`：术语表条目。`locked` 必须照用；`preferred` 是默认译法。
- `history`：本书卷已有的译法及次数、出处。
- `maculaZh`、`ubsZh`：参考简义，不是定译。

规则：

1. 有 `locked` → 必须用该译法，否则该节被拒。
2. 有 `preferred` 或 `history` → 默认沿用；确需不同时，在该 rendering 的 `note` 写理由，否则该节被拒并在 `consistency` 中列出。
3. 都没有 → 这是首次出现，认真选词；重要的词提交后用 `upsert_glossary` 固化。
4. 同一 senseKey 下的正当分化（比喻义与本义、语域差异），写 note 后系统会放行；若这种分化会反复出现，考虑在术语表里按 `senseKey` 分别建条目。

## span（子句合并）

基准是逐句翻译（`span: 1`）。

**判据 A（必须合并）：后置状语造成语序倒置。** 原文把条件、时间、情状成分放在主句之后，中文必须前置——拆开就会留下悬空的尾句。典型形态：

- `אִם`、`כַּאֲשֶׁר`、`בְּטֶרֶם` 引导的后置从句
- `בְּ` / `כְּ` + 不定式的时间从句后置
- `waw` + 独立人称代词 + 分词的情状小句
- 新约中后置的 `ἐάν`、`ὅταν`、`ὡς` 时间/条件从句，同理判断

**判据 B（默认不合并）：中文也可后置的从句。** 原因（`כִּי`、`ὅτι` 表原因、`γάρ`）、关系（`אֲשֶׁר`、关系代词）、目的（`לְמַעַן`、`ἵνα`）从句各自 `span: 1`。引语框架（“神说：”）与引语内容也各自成句。

**判据 C（不得合并）：同型平行对句。** 诗歌体的平行句一律各自成句，即使合并更顺口。

合并写法：

- 合并 N 个连续子句时，首句 `span: N`，其后 N-1 句 `span: 0`、`text: ""`、不给 renderings（renderings 都写在首句上）。
- 合并后的 `text` 用 `\n` 分行，行数与覆盖的子句数一致，**行序按中文语序**。
- 合并不跨节。

## 连词

连词（וְ、καί、δέ、γάρ、οὖν 等）不要死板对译：

- 按它在上下文中的逻辑功能翻译（顺接、转折、因果、结果、解释），或者不译。
- 叙事中串联动作的 וְ / וַ、καί，中文通常不必译出；需要时用“就”“便”“于是”等自然衔接。
- 表示对比、转折、原因、推论时，要把这层逻辑关系译出来（如“却”“因为”“所以”）。
- 连词不要求 rendering，也不纳入用词统一检查。

## 叙事文

- 保留重复结构，不为中文文风删减重复。
- 非主语前置成分有强调或焦点功能，译文要体现。
- 原文明示的主语（尤其重复出现的专名主语）必须译出，不得省为零主语。
